### Indexer health endpoint and startup log can expose the RPC_URL provider key (medium)

- **Fingerprint:** `backend/indexer-health-lasterror-rpc-url`
- **Source:** `backend/cmd/indexer/main.go:143` → `backend/internal/chain/rpc.go:146` → `backend/internal/indexer/step.go:135` → `backend/internal/indexer/engine.go:197` → `backend/internal/indexer/step.go:35` → `backend/cmd/indexer/main.go:110` → `backend/internal/indexer/health.go:93` → `backend/internal/indexer/health.go:150`
- **Lower-trust principal:** A party who can reach the indexer health listener (a host-local user, or another container on the compose network) and sends an unauthenticated GET /healthz while the RPC is failing. No credentials are required.
- **Reproduction:** From agents/v03-backend-indexer-health-lasterror-rpc-url/scratch/backend (copy of backend/ with the toolchain line removed), run in Docker with --network none, --memory 2g, --cpus 2, --pids-limit 512, GOPROXY=off and a read-only module cache: go test ./internal/indexer/ -run TestVerifierRPCURLKeyReachesHealthAndStartupError -count=1 -v (golang:1.26.9, GOTOOLCHAIN=local). The test dials chain.Client to the dummy RPC_URL, runs Engine.Step with OnFailure=HealthTracker.Failed, serves GET /healthz through HealthHandler, and calls VerifyRPCChainID. Read the LastError field of the /healthz body and the VerifyRPCChainID error text.
- **Conditions:** RPC_URL carries a provider credential in its path or query. deploy/backend.env.example:4 says the backend RPC may be credentialed; the production value is not visible in source. An RPC request must fail (connection refused, timeout, or transport error) for LastError to be set. It stays in the snapshot until a later committed state clears it. The listener binds all interfaces by default (INDEXER_HEALTH_ADDR unset). Reach requires host-local access or a peer on the compose network, because compose publishes only 127.0.0.1:8081.
- **Result:** Step error, /healthz body (HTTP 503) LastError, and VerifyRPCChainID error all contain 'http://127.0.0.1:9/v2/DUMMY-KEY-V03-0001'. Test PASS, exit 0. Output in agents/v03-backend-indexer-health-lasterror-rpc-url/artifacts/result.txt (promotion by parent pending). The full cmd/indexer run() was not executed; its wiring (main.go:30, 110, 143) was checked in source.
- **Impact:** Disclosure of a provider API key from an unauthenticated listener, enabling quota abuse or misuse of the key against the provider account.
- **Priority:** likelihood low (Needs a credentialed RPC_URL (documented as possible, not confirmed for production), an RPC failure state, and reach to the listener (host-local or compose network). Not externally reachable by default.) Impact medium.
- **Fix:** Redact at the callers, not inside HealthTracker: pass errors through redact.Error(err, c.RPCURL, c.DatabaseURL) before health.Failed and health.OwnershipLost (the OnFailure and watchdog wiring in cmd/indexer/main.go), and before the slog.Error in main() (main.go:30), matching engine.go:192 and main.go:228. Add a regression test that an RPC url.Error with a dummy key never reaches LastError or the startup log.

### Launch name or symbol with NUL or invalid UTF-8 halts indexer chunk commit (medium)

- **Fingerprint:** `indexer-parse/tokenlaunch-text-utf8-ingest-halt`
- **Source:** `contracts/src/LaunchFactory.sol:76` → `contracts/src/LaunchFactory.sol:128` → `backend/internal/chain/decoder.go:259` → `backend/internal/indexer/router.go:156` → `backend/internal/store/postgres/convert.go:107` → `backend/internal/store/postgres/ledger_inserts.go:215` → `backend/internal/indexer/step.go:77` → `backend/internal/indexer/engine.go:279`
- **Lower-trust principal:** A wallet calls the v1 or v2 launch entry point with a name or symbol containing a 0x00 byte or a non-UTF-8 byte, paying the launch fee and gas. The indexer for that deployment then stops and fails again on every restart until an operator intervenes.
- **Reproduction:** Create a --internal Docker network with no published ports and start postgres:18.6-alpine on it with --read-only, tmpfs-only storage and POSTGRES_HOST_AUTH_METHOD=trust. From a git archive of backend/ at commit 92727e6 in a scratch directory, run go test -tags integration ./internal/store/postgres/postgrestest/ -run TestV13ProbeTokenLaunchTextIngest in golang:1.26.9 with GOTOOLCHAIN=local, GOPROXY=off, and the module cache mounted read-only. The probe re-packs the frozen TokenLaunched fixture with the name replaced, decodes it through chain.NewDecoder, routes it through indexer.LedgerRouter.Apply inside a pgx-pool transaction against a migrated database, and counts token_launches rows. Remove the container and the network after the run.
- **Conditions:** Any wallet that can call the launch entry point, paying the launch fee and gas. Neither factory has an allowlist for launch in the source reviewed. The launch name or symbol contains at least one 0x00 byte, or an invalid UTF-8 byte. The NUL case is rejected on any database encoding; invalid UTF-8 is rejected under the UTF8 server encoding, which the production database encoding does not show in source. The indexer ingests the block that contains the launch through the configured RPC, and the event is committed in the same chunk transaction as its neighbours. No quarantine or skip path exists for an unstorable row. Ingestion resumes only after an operator changes data or code, regardless of the process restart policy. Postgres is the storage dependency. Its rejection of NUL in TEXT is fixed by the server; the production database encoding determines only the invalid-UTF-8 rejection.
- **Result:** Both engines decode the NUL and 0xff names without error. Control inserts 1 row. NUL and 0xff are rejected: ERROR invalid byte sequence for encoding UTF8: 0x00 and 0xff (SQLSTATE 22021), with 0 rows after rollback. Not executed: the Engine.Run restart and process exit, which are source-traced (engine.go:279, main.go:261, step.go:355-378).
- **Impact:** Indexing for the whole deployment stops until an operator changes data or code. No funds, balances or cross-tenant data are affected.
- **Priority:** likelihood medium (Any wallet can trigger it deterministically with one launch whose name or symbol contains a NUL or invalid byte. The only cost is the launch fee and gas.) Impact medium.
- **Fix:** Add one normalization helper for chain-derived text, for example dropping NUL bytes and replacing invalid UTF-8 with U+FFFD, or storing raw bytes in a bytea column through a migration. The owner decides which. Apply it in tokenLaunchParams (v1) and tokenLaunchV2Params so that the insert and TokenLaunchV2MatchesEvent use the same stored value. Do not reject the launch, since a rejected event would desynchronize the indexer. Add regression fixtures with 0x00 and 0xff in name and symbol that assert the chunk commits and a replay matches.

### Alerts keep reaching a chat after /stop or web unlink within the in-flight pass (low)

- **Fingerprint:** `telegram:delivery-pass-stale-link-after-unlink`
- **Source:** `backend/internal/telegram/worker.go:140` → `backend/internal/telegram/worker.go:72` → `backend/internal/telegram/worker.go:81` → `backend/internal/store/postgres/telegram_store.go:180` → `backend/internal/telegram/worker.go:86`
- **Lower-trust principal:** A linked chat holder, or the account owner, revokes delivery while a pass is sending. For the variant, a holder of a valid code for account B re-binds the chat during the window to receive account A's queued alerts. Reproduced with an in-package probe using dummy principals did:privy:A and did:privy:B and chat 42.
- **Reproduction:** git archive 92727e6 backend into a scratch directory, then delete the toolchain line from go.mod (the sandbox image is go1.26.9). Add zz_probe_stale_delivery_test.go (package telegram) with in-memory DeliveryStore and Sender stand-ins. The Sender runs the revocation inside its first alert send, after that send is recorded. The store's Advance mirrors the chat_id guard, and ClaimCode mirrors the other-account delete. Run in golang:1.26.9 with --network none, --memory 2g, --cpus 2, --pids-limit 512, GOPROXY=off, read-only module cache: go test ./internal/telegram/ -run TestProbe -count=1 -v. Read the scenario lines in agents/v30-am-delivery-pass-stale-link-after-unlink/artifacts/result.txt (lines 19 and 32).
- **Conditions:** A /stop from the linked chat, or DELETE /v1/me/telegram by the account, lands after a pass has fetched pending events for that link. The revocation must fall inside the in-flight batch (up to 10 sends, 40 ms pace plus Telegram API latency). Passes run every 5 s and send only when events are pending, so the window opens only while a batch is in progress. The link has pending events that match its settings when the pass snapshots it. Variant only: for the cross-account effect, a valid link code for a second account (15-minute TTL, telegram.go:24) must be claimed on the same chat inside the same window.
- **Result:** Scenario A: /stop deleted the row, Advance matched 0 rows and returned nil, and alert sends e2 and e3 went to chat 42 after the unlink (2 sends); pass 2 sent 0. Scenario B: after the chat was re-bound to did:privy:B, account A's e2 and e3 went to chat 42 (2 sends) and Advance for A matched 0 rows. Both tests PASS, exit 0. The interleaving was injected deterministically, not produced by real concurrency, Postgres or Telegram; no live endpoint was contacted.
- **Impact:** Same account: up to 10 unwanted alerts after /stop or unlink, for on-chain events the account watches. Variant: up to 10 alert texts of account A (filtered by A's watchlist) to a chat re-bound to B. No funds, auth or cross-tenant write is involved.
- **Priority:** likelihood low (Needs a revocation to land inside a multi-event batch. Passes run every 5 s and send only pending events, so the window is narrow in practice.) Impact low.
- **Fix:** Before each SendMessage, re-read the link and send only while the row still has the same privy_did and chat_id; on mismatch, stop that link's batch. This leaves at most the one request already in flight, which a pre-send check cannot close, so the spec should state that residual.

### Receipt-wait transport error or timeout is recorded as receipt-reverted and releases the submission lock (low)

- **Reproduction:** Mount the repository read-only at /target and the agent scratch directory read-only at /scratch, then run: docker run --rm --network none --read-only --tmpfs /tmp:rw,size=64m --cpus 2 --memory 1g --pids-limit 64 -v <repo>:/target:ro -v <scratch>:/scratch:ro node:22 node --experimental-strip-types /scratch/check.mjs The script imports web/src/transaction-errors.ts from the read-only target, reads the unresolved status list from web/src/transactions-panel/shared.tsx, reads the observer line from transaction-persistence.ts, and applies the candidate remediation to an in-memory copy under /tmp. Read the factual output at agents/v36-e-transport-error-classified-as-reverted/artifacts/result.txt after promotion.
- **Conditions:** The receipt wait rejects before the transaction is observed as mined: viem's 180 s default timeout on a slow or congested chain, or an RPC error during polling. The configured RPC endpoint behind publicClient must fail or stall during the receipt wait (reviewed-trade.tsx:241). The user must re-submit the same buy or sell after seeing receipt-reverted. No recheck runs for that status. The first transaction actually mines and succeeds, which the UI never observes.
- **Result:** Sandbox node v22.23.4 on the 92727e6 sources (identical at HEAD). Receipt phase with 'Failed to fetch' -> receipt-reverted; receipt phase with the viem timeout template -> receipt-reverted; receipt phase with 'ReceiptReverted' -> receipt-reverted; write phase with 'Failed to fetch' -> rpc-failure. With the one-line remediation applied in memory: receipt phase with transport error or timeout -> rpc-failure; receipt phase with ReceiptReverted -> receipt-reverted. - **Impact:** A user may buy or sell twice with their own funds after a misreported outcome. Claims are not doubled because the NothingToClaim preflight blocks a second claim. No third party or custody is involved.
- **Priority:** likelihood low (Requires an RPC failure or a 180 s timeout during the receipt wait, followed by a user re-submission of the same action after seeing receipt-reverted.) Impact medium.
- **Fix:** In the receipt phase, report receipt-reverted only for the on-chain status failure (the ReceiptReverted error thrown at reviewed-trade.tsx:242 and direct-write.ts:84) and report any other wait error as rpc-failure while keeping the hash, so hasUnresolvedSubmission blocks the next action and the observer keeps running. The classifier is shared, so direct-write.ts is covered by the same change. Update the expectation at transactions-task6.test.ts:253-255, which asserts receipt-reverted for 'execution reverted' in the receipt phase and would return rpc-failure under the fix, and add transport and timeout cases for the receipt phase. reviewed-trade.test.tsx:206 and direct-write.test.ts:84-86 use a reverted status and stay valid.
